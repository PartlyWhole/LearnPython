# Levels

The levels, in play order (`lessons/index.json`, expanded by `tools/play_order.py`). Each is our own world and wording.
The problem *shapes* are adapted from the Code in Place / CS106A Karel problems catalogued in
`docs/research/code_in_place_problems.md`. Nothing is copied.

**Drive levels (Unit "Meet the robot").** They are played with buttons, not code (`"drive"` in the level;
`docs/lessons.md` §3). Each press adds a command to a program the engine runs. They have no hidden
worlds on purpose: the learner drives the world they can see.

## Authoring a level

1. Write `levels/<id>.json` (schema: `schemas/level.schema.json`): world, hidden worlds aimed at the
   edge cases (1×1, a single row, an empty world, something on the start cell, odd and even sizes),
   goal, constraints and topic IDs.
2. Write the reference solution `tests/solutions/<id>.py`, and at least one
   `tests/solutions/<id>.wrong_<what>.py` for the mistake the level is built around.
3. If goals differ per world, fill them from the reference:
   `python3 tools/level_goals.py <id> --fields gems_exactly --write` (or `end_at`, `facing`). This makes
   goals agree with the reference *by construction*, so check the printed values yourself.
4. Put the level in the play order, `lessons/index.json`: in its lesson's `practice` or `twist` (or `guided`), or as a `{"level": id}` item.
5. `python3 -m pytest -q tests`. `test_levels.py` checks that the reference passes, every wrong
   solution fails, the starter code does not already pass, and per-world goals come with hidden worlds.
6. Play it in `app.html` and look at the replay: tests can't tell you whether a world reads well.

Gotcha found while authoring `hurdles`: Karel's walls sit *between* cells, but our blocked cells
fill them. Karel solutions often need an extra step to cross or round an obstacle here.
